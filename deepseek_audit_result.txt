## 1. [SDV 플랫폼 적합성 및 차별성] — 17/25

### 긍정 평가
- **"화면 표시형 앱"이 아닌 물리 액추에이터 제어**라는 포지셔닝은 공모전이 명시적으로 원하는 SDV 킬러 앱의 정의에 부합합니다. 심사위원 관점에서 "이 앱이 없으면 차량이 못 하는 일"이 명확하다는 점은 강한 차별화 요소입니다.
- 음성 인텐트 → 시트 모터 → TTS 피드백의 **closed-loop 시나리오**는 데모 영상에서 임팩트가 큽니다.

### 냉정한 지적
1. **"Pleos Vehicle SDK"라는 명칭의 실체 확인 필요.** 공모전 주최측이 배포한 실제 SDK 명세(패키지명, `SeatManager` 클래스 존재 여부, 권한 모델)와 코드가 일치하는지 증빙이 없습니다. 코드에는 `PleosVehicleController`가 **자체 정의한 data class와 MutableStateFlow만으로 시뮬레이션**하고 있어, 실제 SDK 호출(`SeatManager.setLumbar(...)` 등)이 **단 한 줄도 없습니다.** 심사위원이 코드를 열어보는 순간 "이건 SDK 연동이 아니라 상태 머신 흉내"라는 판단이 즉시 나옵니다.
2. **AAOS Car API와의 관계 정리 부재.** AAOS에는 `CarPropertyManager`의 `HVAC`/`SEAT` 관련 property ID가 존재합니다. Pleos SDK가 이를 래핑한 것인지, 독자 규격인지 명시해야 "왜 Pleos SDK여야 하는가"에 답할 수 있습니다.
3. **차별성 서사는 좋으나 경쟁 앱 대비 우위 근거 약함.** "음성으로 시트 조절"은 이미 일부 프리미엄 차량(제네시스 등)에 존재. 차별점은 **"누적 피로 예측 기반 선제 제어"** 인데, 이 부분의 알고리즘이 코드에 전무합니다(아래 3항 참조).

**보강 지시:** 실제 SDK 스텁이라도 `SeatManager` 인터페이스를 주입(DI)받아 호출하는 구조로 리팩터링하고, README에 "SDK 계약 명세 대조표"를 첨부하십시오.

## 2. [차량 안전 가이드라인 / Safety Interlock] — 12/25 ⚠️ **최대 리스크**

### 치명적 결함: Interlock이 "기획서에만" 존재
기획서 4번 항목은 "급가속·급선회·고속 주행 시 시트 제어 자동 보류"를 **핵심 안전 기능**으로 내세웁니다. 그러나 제출된 `PleosVehicleController.kt`에는:

- `currentSpeedKmH`, `continuousDrivingMinutes`가 **data class의 기본값(35, 80)으로 하드코딩**되어 있을 뿐, 실제 텔레메트리 구독 코드가 없습니다.
- `applySpineCareRelief()`는 **속도·조향·기어 상태를 전혀 검사하지 않고 즉시 모터 값을 변경**합니다.
- 즉, **기획서의 Safety Interlock은 코드에 0% 구현되어 있지 않습니다.** 이는 심사위원이 가장 먼저 지적할 "기획-구현 괴리"입니다.

### 규제·법적 리스크 (반드시 인지)
1. **UN R79 / FMVSS 126 (조향·주행 안정성)**: 주행 중 시트 등받이 각도 변경은 운전자의 조향 반응 시간에 영향을 줄 수 있습니다. **주행 중 리클라인 각도 변경은 대부분의 OEM 내부 규정상 금지 또는 극히 제한**됩니다. "2도 미세 조정"이라도 **주행 중 자동 실행은 규제 검토 대상**입니다.
2. **ISO 26262 (기능 안전)**: 시트 모터 제어가 ASIL 등급 대상인지 명시 필요. 최소 QM~ASIL-A 수준의 안전 요구사항 도출이 필요합니다.
3. **UN R17 (시트 강도)**: 시트 구조 변경이 아닌 모터 제어이므로 직접 위반은 아니나, **에르고 모션 마사지 자동 가동**은 운전자 주의 분산(ISO 15008 / NHTSA distraction guideline) 검토 대상입니다.
4. **개인정보**: "통증 이력"은 **민감정보(건강정보)** 로 분류될 소지가 큼 → GDPR/PIPA 관점의 별도 동의·암호화 필요.

### 요구 보강 (본선 전 필수)
```kotlin
// 반드시 추가해야 할 안전 게이트 예시
private fun isSafeToActuate(): Boolean {
    val s = _seatState.value
    return s.currentSpeedKmH < 5 &&           // 정차/저속만 허용
           gearState == Gear.PARK || gearState == Gear.NEUTRAL &&
           !isSharpTurnDetected() &&
           !isEmergencyBraking()
}
```
그리고 **주행 중에는 "리클라인 각도 변경 금지, 요추 지지대만 소폭 허용"** 으로 정책을 명확히 분리하십시오. 이 정책 분리 자체가 심사위원에게 "안전을 이해하는 팀"이라는 강한 인상을 줍니다.

## 3. [개인화 헬스케어 실효성] — 18/25

### 긍정
- "운전자 A는 45분 경과 시 요추 4~5번 부담 급증" 같은 **서사적 개인화**는 PT에서 설득력이 높습니다.
- Room DB 오프라인 로그 설계는 SDV 환경(터널·음영)에서 타당합니다.

### 냉정한 지적
1. **"통증 패턴 메모리"의 알고리즘이 코드에 없음.** `PleosVehicleController`는 상태 머신일 뿐, **누적 학습·예측 로직이 전무**합니다. 기획서의 "선제적 제안"은 현재 **구현 불가능한 마케팅 문구**입니다.
2. **의학적 근거 부재.** "요추 4~5번"이라는 특정 척추 분절 언급은 **의료 행위로 오인될 소지**가 있습니다. 앱이 "진단"이 아니라 "편의 제어"임을 명확히 하고, **의료기기법(식약처) 비해당 포지셔닝**을 기획서에 명시해야 합니다. 그렇지 않으면 규제 리스크로 감점됩니다.
3. **검증 데이터 부재.** "허리 부담 28% 경감"이라는 리포트 수치는 **어떤 근거로 산출했는지** 명시 필요. 근거 없는 수치는 심사위원의 신뢰를 훼손합니다. → "압력 분포 시뮬레이션 기반 추정치" 등으로 정직하게 표기하십시오.
4. **개인화의 콜드 스타트 문제.** 신규 탑승자는 데이터가 없습니다. 초기 기본값 정책과 "학습까지 N회 필요" 안내 UX가 필요합니다.
